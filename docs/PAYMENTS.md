# Платежи и подписки

## Режимы

| Режим | Поведение |
| --- | --- |
| `local` | Встроенный `FakePaymentProvider`. Оформление и подтверждение требуют `FAKE_PAYMENT_SECRET`. |
| `pilot` | Тестовые подписки доступны участникам закрытого пилота при явном `ALLOW_FAKE_PAYMENTS=true` и отдельном стойком `FAKE_PAYMENT_SECRET`. Значения для локального примера заменяют собственными. |
| `production` | Конфигурация отклоняется при запуске. Для коммерческого режима требуется подключить реальный адаптер и зарегистрировать его в настройках. |

Секрет подписи хранится на сервере. Веб-интерфейс использует защищённые маршруты тестового оформления и помечает подписку как тестовую. Пилот и будущий коммерческий сервис используют раздельные базы, учётные записи, секреты и хранилища.

## Как проверяется состояние

Оформление сохраняет снимок тарифа и стабильный идентификатор до вызова платёжного адаптера. Повтор после ошибки использует тот же идентификатор. Подписка активируется по проверенному серверному уведомлению. Тестовый маршрут подтверждения генерирует такое уведомление внутри сервера и использует общий обработчик событий.

Подписанный webhook обрабатывается в транзакции с блокировкой учителя. Уже записанный идентификатор события не создаёт второй период или лимит. Повторное использование идентификатора для другого оформления, типа или версии возвращает 409. Запоздавшее событие с версией ниже или равной последней применённой не меняет подписку. Отклонённое пересечение периодов сохраняется для дедупликации и оставляет версию подписки прежней.

Продление создаёт новый период и новый лимит в момент его начала. Отмена продления сохраняет уже выданный доступ до конца периода. При проверке работы лимит резервируется сразу, окончательный сбой освобождает резерв. Доступ к оформлению и статусу подписки защищён учётной записью учителя.

```powershell
python -m pytest -q tests/test_billing.py
```

Конкурентный сценарий PostgreSQL запускается с `TEST_DATABASE_URL` тестового экземпляра, где можно создавать временные схемы. Тесты внешнего интерфейса используют адаптер-двойник.

## Подключение коммерческого адаптера

1. Выбрать страну запуска и провайдера, получить тестовый аккаунт и официальную документацию. Отдельно согласовать тарифы, валюту, цены, автопродление, отмену, возвраты, чеки и работу поддержки.
2. Реализовать `PaymentProvider`. В `checkout(CheckoutIntent)` передавать замороженную сумму и валюту из базы, использовать `checkout_id` как ключ идемпотентности и корреляции. Проверять допустимый HTTPS-хост размещённой платёжной страницы. Платёжные реквизиты вводятся на странице провайдера.
3. В `parse_event(raw_body, headers)` проверять подлинность исходного тела и допустимое время доставки согласно протоколу провайдера. Проверять расчёт и состояние подписки через серверный API провайдера. Передавать в нормализованном платёжном событии подтверждённые сумму, валюту, период, идентификатор внешней подписки и версию. Бэкенд сверяет идентификатор, сумму и валюту со снимком оформления. Для провайдера без монотонных версий понадобится сверка состояния или другой механизм упорядочивания. [Рекомендации OWASP по платёжным интеграциям](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Payment_Gateway_Integration_Cheat_Sheet.html).
4. Согласовать поведение для отменённых или заменённых платёжных сессий, просроченных уведомлений, спорных платежей, возвратов и неизвестного результата сетевого запроса. Реализовать сверку расхождений с провайдером и операционные оповещения. Для подтверждений и отмен проверять идемпотентность на стороне провайдера.
5. Добавить коммерческий каталог, интеграцию размещённого checkout в браузере и маршрутизацию реального адаптера. Проверить весь цикл в песочнице провайдера, включая ошибку и повтор доставки webhook, отмену, продление и несоответствие суммы. Перед переключением режима проверить изоляцию пилотных подписок и данных.

Адаптер-двойник проверяет внутренний контракт. Реальный провайдер, его аккаунт и коммерческий каталог ещё не подключены.
