# Эксплуатация закрытого пилота

Пилотная конфигурация рассчитана на выделенный Linux-хост с Docker Engine и Compose v2, локальными PostgreSQL и Redis, внешним приватным S3-совместимым хранилищем по HTTPS и TLS-прокси на том же хосте. Это односерверная схема. Изолируйте хост в VPN или в сети организации и ограничьте входящий 443 разрешёнными подсетями. Владельцу предстоит выбрать хост, регион БД, регион и провайдера S3, домен, доверенные сети, сроки хранения, роли доступа и оператора. Используйте синтетические работы и FakeAIProvider до согласования передачи данных.

[Пилотный Compose](../deploy/compose.pilot.yaml) запускается отдельно от локального `compose.yaml`. Только сайт слушает порт хоста на `127.0.0.1:5173`. Браузер обращается к сайту и `/v1` через один HTTPS origin. PostgreSQL и Redis доступны контейнерам в изолированной сети, соединения аутентифицируются. Миграции выполняет отдельная роль-владелец схемы. Роль API и воркера получает доступ на чтение и изменение таблиц, без прав менять схему. Для пилота выделите отдельный S3-бакет, учётные данные и резервные копии. API и воркер работают с отдельной учётной записью бакета, которую создаёт оператор, а резервные копии читает отдельная операторская роль.

## Подготовка конфигурации

1. Создайте вне репозитория защищённый каталог для конфигурации и секретов, например `/etc/suhoy-ostatok`. Скопируйте [образец](../deploy/pilot.env.example) в `pilot.env`. Заполните `PILOT_RELEASE` уникальным идентификатором сборки, `PILOT_APP_ENV_FILE` и `PILOT_SECRETS_DIR` абсолютными путями, `PUBLIC_ORIGIN` полным HTTPS origin, а также `S3_ENDPOINT_URL`, `S3_BUCKET` и `S3_REGION`.
2. Создайте файлы `postgres_admin_password`, `postgres_migration_password`, `postgres_runtime_password` и `redis_password` независимыми вызовами `openssl rand -hex 32`. Аналогично задайте отдельные `fake_payment_secret` и `pilot_access_code`. В `pilot_allowed_emails` храните JSON-массив разрешённых учётных записей. Запишите выданные хранилищем значения в `s3_access_key` и `s3_secret_key`. Создайте пустой файл `gemini_api_key` для FakeAIProvider. Оставьте `AI_PROVIDER=fake` и `ALLOW_FAKE_PAYMENTS=true` для пилота с тестовыми расчётами. Переход на Gemini отдельно требует согласия владельца, `ALLOW_EXTERNAL_AI=true` и действующего ключа. Платёжное уведомление по публичному пути блокируется прокси. Тестовое подтверждение в интерфейсе работает через отдельный закрытый маршрут.
3. Храните файлы секретов с режимом `0400` и доступом UID 10001 (UID контейнера API). Административный и миграционный пароль нужны процессу инициализации PostgreSQL. Пароль миграций также нужен UID 10001. Проверьте права в контейнерах, особенно при rootless Docker и переназначении UID. Доступ к Docker-сокету должен оставаться у операторов. Режимы PostgreSQL и исходные пароли применяются при первом запуске чистого тома. Для ротации сначала измените пароль роли PostgreSQL согласованной административной операцией, затем обновите секрет и пересоздайте затронутые сервисы. Ротацию Redis проводите при остановленных писателях и затем пересоздайте Redis, API и воркер.
4. В бакете запретите публичные ACL и политики. Дайте учётной записи приложения только проверку бакета и `GetObject`, `PutObject`, `DeleteObject` для `submissions/*`. Для AWS S3 проверка через HeadBucket требует `s3:ListBucket`; проверьте точные действия на выбранном хранилище и доступ к ключу шифрования, если применяется KMS. Пилотный Compose ожидает заранее созданный бакет. Для бэкапа и восстановления задайте раздельные учётные записи. Согласуйте версионирование, удаление версий и резервных копий до загрузки пользовательских данных.
5. Установите сертификат и адаптируйте [конфигурацию Nginx](../deploy/nginx-pilot.conf.example). Замените служебный адрес на реальные CIDR VPN или офиса, ограничьте 443 на файрволе и проверьте `nginx -t`. Образец рассчитан на прямой вход в Nginx. Если перед ним стоит балансировщик, перенесите ограничение источников на балансировщик либо настройте приём клиентского IP только от доверенного прокси и запретите обход. Node и Uvicorn не доверяют клиентским forwarded-заголовкам. При работе нескольких учителей за одним NAT измерьте эффект общего лимита по IP.

[Секреты Docker Compose](https://docs.docker.com/reference/compose-file/secrets/) · [Лимиты Nginx](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html) · [Проксирование Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).

## Запуск и проверка

Выполняйте команды в корне проекта. Договоритесь о коротком окне обслуживания для первого запуска и обновлений.

```bash
dc() { docker compose --env-file /etc/suhoy-ostatok/pilot.env -f deploy/compose.pilot.yaml "$@"; }
dc config --quiet
dc build
dc up -d
dc ps -a
dc logs --tail=50 migrate api worker site
dc exec -T api python -c "from urllib.request import urlopen; print(urlopen('http://127.0.0.1:8000/health/ready',timeout=5).status)"
```

На разрешённом клиенте проверьте цепочку сертификата без обхода проверки TLS и откройте сайт. Проверьте `/v1/plans`, отказ регистрации без доступа и вход приглашённой учётной записи. Запустите синтетическую проверку, дождитесь завершения, откройте страницу с авторизацией, исправьте, перепроверьте и удалите работу. Проверьте, что вызов из неразрешённой сети закрыт. Извне API:8000, Redis, PostgreSQL и сайт:5173 должны быть недоступны. Проверка `migrate` должна завершиться с кодом 0. Проверка воркера измеряет свежесть файла heartbeat. Локальная готовность API проверяет БД, Redis и S3, а готовность сайта проверяет цепочку сайта и API. Для устойчивой проверки воркера нужен синтетический проход целиком. Healthcheck Docker отмечает контейнер как unhealthy, а наблюдатель должен отдельно сигнализировать об этом состоянии.

## Мониторинг

- Оповещайте оператора при трёх последовательных неудачах проверки HTTPS или внутренней готовности, при unhealthy воркере, ошибках БД, Redis, S3 и заполнении томов. Используйте HTTP-методы без работ учеников и закрытый мониторинговый доступ.
- Отслеживайте число `queued` и `processing`, время самой старой работы в очереди, терминальные ошибки и их долю, восстановление истёкших lease, остаток диска, возраст последней резервной копии и срок сертификата. Для пилота начните с расследования очереди дольше 5 минут и пересмотрите порог после замеров. Проверяйте причину и восстановление воркера перед ручным повтором. Не очищайте очередь при недоступном Redis.
- Ограничьте доступ к журналам и их срок хранения. Сопоставляйте `request_id` и идентификаторы заданий по JSON-событиям. Не передавайте тела запросов, файлы, заголовки авторизации или значения секретов в системы мониторинга.

```sql
SELECT status, count(*) AS jobs,
       CASE WHEN status = 'queued' THEN now() - min(created_at) END AS oldest_wait
FROM processing_jobs
WHERE status IN ('queued', 'processing')
GROUP BY status;
```

## Резервная копия и тест восстановления

Оператору нужны отдельный зашифрованный каталог вне томов Compose, AWS CLI или совместимый клиент выбранного провайдера и право чтения бакета. Выполняйте снимок в окно остановки записи, приостановив сайт, API, воркер и любые внешние операции с бакетом. Дождитесь завершения остановки. Каталог `backup` ниже должен быть новым и пустым. Включите защиту копий от удаления, определите периодичность и срок хранения. Не копируйте ключи приложения вместе с данными.

```bash
set -euo pipefail
umask 077
backup="/encrypted/backup/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir "$backup"
mkdir "$backup/objects"
trap 'dc up -d site api worker' EXIT
dc stop site api worker
dc exec -T postgres pg_dump -U postgres -d stopkadr -Fc --no-owner --no-acl > "$backup/db.dump"
dc exec -T postgres pg_restore --list < "$backup/db.dump" > "$backup/db.contents"
dc exec -T postgres psql -XAt -U postgres -d stopkadr -v ON_ERROR_STOP=1 -c   'SELECT object_key FROM submission_files UNION SELECT object_key FROM submission_pages ORDER BY 1'   > "$backup/references.txt"
aws --profile pilot-backup --endpoint-url "$S3_ENDPOINT_URL" s3 sync   "s3://$S3_BUCKET/submissions/" "$backup/objects/submissions/"
while IFS= read -r object; do test -f "$backup/objects/$object"; done < "$backup/references.txt"
(cd "$backup" && find db.dump db.contents references.txt objects -type f -print0 | sort -z | xargs -0 sha256sum > SHA256SUMS)
touch "$backup/COMPLETE"
dc up -d site api worker
trap - EXIT
```

При сбое копирования сохраните работающий экземпляр, зафиксируйте ошибку и не маркируйте неполную копию как пригодную. Для проверки восстановления используйте отдельный Compose project, например `docker compose -p stopkadr-restore`, чистые тома, отдельный конфигурационный файл и отдельный пустой бакет. Не выставляйте восстановленное окружение в сеть и не включайте внешние вызовы. При проверке восстановления параллельно с пилотом используйте другой хост или замените loopback-порт сайта в копии Compose.

1. Выполните `(cd "$backup" && test -f COMPLETE && sha256sum -c SHA256SUMS)`. Запустите PostgreSQL и Redis восстановления, дождитесь `healthy`. В командах ниже `restore` обозначает Compose с отдельными project и env-file.
2. Восстановите SQL в чистую БД и объекты в отдельный бакет. Роль миграции уже создана и имеет нужные права на схему. Redis можно начать с пустого тома. Воркер восстанавливает очередь по БД, включая просроченные аренды.
3. Выгрузите список ссылок той же SQL-командой, сравните с `references.txt`, проверьте наличие объектов в целевом бакете и откройте страницу существующей синтетической работы. Запустите проверку с FakeAIProvider, убедитесь в сохранении прав доступа и удалении данных. Зафиксируйте длительность восстановления, ревизию схемы и возраст данных.

```bash
restore exec -T postgres pg_restore -U postgres -d stopkadr   --role=stopkadr_migrator --no-owner --no-acl --exit-on-error --single-transaction   < "$backup/db.dump"
aws --profile pilot-restore --endpoint-url "$RESTORE_S3_ENDPOINT_URL" s3 sync   "$backup/objects/submissions/" "s3://$RESTORE_S3_BUCKET/submissions/"
restore up -d
```

Целевые RPO и RTO задаёт владелец после теста восстановления. PostgreSQL и S3 хранят разные части состояния, поэтому их копии и восстановление должны быть согласованы. [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) · [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

## Обновление и откат

Перед обновлением выполните браузерные тесты в отдельной среде, зафиксируйте текущий `PILOT_RELEASE` и ревизию Alembic, подготовьте согласованный снимок. Соберите образы новой версии под новым тегом. На время миграции остановите запись, дождитесь завершения текущих задач и запустите `dc up -d`. После изменения проверьте миграцию, готовность и синтетическую работу. Старые теги и снимки сохраняйте до подтверждения проверки. Если схема совместима со старым кодом, верните предыдущий тег. Если совместимость отсутствует, поднимите согласованный снимок базы и бакета в отдельном окружении, проверьте его и переключите TLS-прокси только после восстановления. Данные после снимка могут потребовать ручного переноса по согласованию с владельцем.

## Что проверять на хосте пилота

Проверка схемы Compose и скриптов на рабочей машине не заменяет запуск Linux-контейнеров. На выбранном хосте отдельно подтвердите TLS, изоляцию сетей, входной лимит, доступ приложения к конкретному бакету, политику удаления, время восстановления, работу сертификата и эксплуатационные оповещения. Реальные ключи, хост, домен, сертификат и бакет для пилота требуют подготовки владельцем.
